# Test audit

## Scope

- Audit only test files added or changed on the working branch, as shown by `git diff <base>...HEAD`.
- Also audit production code those tests reach when it exists only to serve tests (test-only seams).
- Do not sweep the whole repository.

## What a test is for

- Every test protects an observable behaviour, invariant or contract.
- A credible regression in that behaviour makes the test fail.
- Each contract has one primary owner at the strongest boundary that can observe it; do not duplicate it at every layer.
- Behaviour-preserving refactors should not break tests.

## Junk patterns to remove or rewrite

- **Self-comparisons** — assertions compare a value with itself instead of checking the intended result.
- **Copied inventories** — tests restate a list from the source without protecting an independent contract.
- **Source greps** — tests inspect source text instead of exercising observable behaviour.
- **Implementation or call-shape assertions** — tests lock in internal structure or how a function is called rather than its contract.
- **Duplicate contracts** — multiple tests own the same contract at equivalent or weaker boundaries.
- **Test-only production seams** — production code exists only to make tests easier instead of serving users or a real integration boundary.
- **Expected values generated by the subject under test** — the test derives its expected result from the same code it is checking.
- **Mocks that supply the very behaviour being asserted** — a mock makes the assertion pass without exercising that behaviour.
- **Fixtures that fabricate state the real path never writes** — tests rely on impossible or unrepresentative state.
- **Negative controls that do not fail at the intended guard** — the control does not prove that the target check rejects the case.
- **Test names that do not match the behaviour actually exercised** — names promise coverage the test does not provide.

## Retention bar

- Keep tests that independently own an API, protocol, config, migration, storage, security, default-value or ordering contract.
- Being static or slow does not make a test disposable.
- A test that fails on the baseline may expose a bug to fix, not a test to delete.

## How to report

- Never optimise for deletion counts.
- Each finding names `file:line`, the rubric item it violates, and a fix: delete, rewrite to assert X, or move to boundary Y.
- Output findings in this format:

  ```text
  findings:
  1. path/to/file:LINE — what to change, and why (rubric item)
  2. ...
  ```

- If there are no findings, output `no findings`.
- Production bug fixes are outside polish scope. Report any production bug separately under `notes:` after the findings; the orchestrator relays notes to the user and does not apply them. If there are notes but no findings, output `no findings` followed by the `notes:` block.

  ```text
  no findings
  notes:
  - path/to/file:LINE — production bug to report
  ```
